# Security policy and threat model

## Supported versions and reporting

Security fixes are made on the current development branch and shipped in the next release. Only the latest release is supported; older release lines are not maintained.

Please report suspected vulnerabilities privately through GitHub's **Report a vulnerability** / private vulnerability reporting feature for this repository, if enabled. If it is unavailable, write to [security@taskbrigade.dev](mailto:security@taskbrigade.dev). Do not put exploit details, credentials, or private task contents in a public issue. Include the affected version or commit, deployment configuration, reproduction steps, impact, and any suggested mitigation. Maintainers will acknowledge and coordinate a fix and disclosure; there is no promised response time or bug bounty.

## Assets, actors, and trust boundaries

TaskBrigade stores tasks, comments, project metadata, API-token hashes, password hashes, encrypted Gitea tokens and settings, and a separately stored Fernet master key. It can also direct agents to clone, edit, and push project repositories. Protect the task database, repository contents, Gitea credentials, session-signing key, master key, and the agent host's filesystem.

The intended deployment is a single trusted host running Uvicorn without proxy-header processing (`--no-proxy-headers`), bound to `127.0.0.1`. `tailscale serve` terminates HTTPS and connects to that local listener. TaskBrigade trusts `Tailscale-User-Login` only when the **direct peer** is loopback (or listed in `TRUSTED_PEER_NETWORKS`) and the login is in `UI_ALLOWED_LOGINS`. A permitted login mapped to an active human actor receives that actor's role. An allowed but unmapped login receives bootstrap access; keep this list small and map users deliberately. A process able to connect to the local listener can forge this header. Loopback is therefore a trusted boundary, not proof that a request came from Tailscale. Do not run untrusted users or processes on the application host, and do not forward an untrusted proxy into the local listener.

With network enforcement enabled, loopback can reach the UI and API. `LAN_UI_NETWORKS` can permit direct HTTP access to the UI, while `/api/` remains blocked for those peers; all other direct peers receive 403. The network policy uses the socket peer, not `X-Forwarded-For` or `X-Forwarded-Proto`. Keep Uvicorn's `--no-proxy-headers`, network enforcement, firewall rules, and the bind address aligned. A different reverse proxy or container network requires a fresh review of these assumptions. `TRUSTED_PEER_NETWORKS` extends the loopback trust to the listed CIDRs (see the container section below). `API_NETWORKS` (empty by default) is an explicit opt-in that lets the listed peers use the UI and the API over plain HTTP; it does not extend loopback trust. Do not expose port 8090 to the internet. Prefer HTTPS through Tailscale; direct LAN UI traffic carries passwords and session cookies in cleartext, and `API_NETWORKS` traffic additionally carries API tokens.

## Container deployment (Docker Compose)

Inside a container the direct peer is a Docker address, not the host's loopback. The trust model above is kept by the following rules; `docs/docker.md` has the setup.

| Peer class | UI | API | `Tailscale-User-Login` and git credentials |
| --- | --- | --- | --- |
| Loopback and `TRUSTED_PEER_NETWORKS` | yes | yes | yes |
| `API_NETWORKS` | yes | yes | no |
| `LAN_UI_NETWORKS` | yes | no | no |
| Anything else | no (403) | no (403) | no |

- **Default (no sidecar).** The port is published on `127.0.0.1:8090` of the Docker host. Connections through it arrive from the bridge gateway, which Compose lists as the only `TRUSTED_PEER_NETWORKS` entry (`172.31.250.1/32` of a pinned subnet). Every process on the Docker host is therefore trusted like a local process on a native server: it can use the API with a token, forge `Tailscale-User-Login` and, with a token, fetch Gitea credentials. Other containers on the Compose network keep their own addresses and are rejected; MariaDB is not published. Never list a LAN or a whole container network in `TRUSTED_PEER_NETWORKS`.
- **Tailscale sidecar (`compose.tailscale.yaml`).** TaskBrigade shares the network namespace of the `tailscale/tailscale` container; `tailscale serve` terminates HTTPS and connects to `127.0.0.1:8090` inside that namespace, so the identity header arrives from loopback as on a native server. Funnel is disabled in the serve config. The sidecar's node key and state are in the `taskbrigade-tailscale-state` volume; whoever obtains it can impersonate the node in the tailnet. `TS_AUTHKEY` is also passed to the app container through `.env`; remove it after the first start. Every process in the shared namespace (the sidecar and the app) and every process on the Docker host that reaches the published port can forge the identity header – the same boundary as loopback on a native server. Restrict which tailnet users and devices may reach the node with Tailscale ACLs; `UI_ALLOWED_LOGINS` decides who may sign in.
- **LAN without Tailscale.** `TBR_PUBLISH` beyond `127.0.0.1` exposes the listener. `LAN_UI_NETWORKS` admits the UI (passwords and session cookies in cleartext). `API_NETWORKS` admits the API as a deliberate, documented decision: bearer tokens travel in cleartext and a passive observer can take over that actor. Keep it to single agent hosts on a trusted segment. These peers never get identity-header trust or Gitea credentials. Startup validation rejects malformed CIDRs and `/0` in all three settings, and the server logs `api_networks_cleartext` when `API_NETWORKS` is set.
- **Gateway rewriting.** Docker Desktop (macOS, Windows) and Docker's userland proxy (for example IPv6 clients of an IPv4 container) present every client as the gateway address. With `TBR_PUBLISH` beyond `127.0.0.1` every client that reaches the port is then trusted like loopback, and `LAN_UI_NETWORKS`/`API_NETWORKS` have no effect. On those platforms keep the default publish address and use the sidecar or a TLS proxy.
- **TLS reverse proxy.** The recommended way to serve a LAN without Tailscale is a reverse proxy with TLS on the Docker host forwarding to `127.0.0.1:8090`. It arrives as the trusted gateway, so it **must** strip `Tailscale-User-Login` from client requests; otherwise every client can claim an allowed login. The proxy also hides client addresses from login rate limiting and the network policy, so restrict access at the proxy or firewall.
- **Container hardening.** The app runs as an unprivileged user (uid 10001) with one Uvicorn worker and `--no-proxy-headers`. `master.key` and `secret.key` live in the `taskbrigade-state` volume and the database in `taskbrigade-db`; anyone with access to the Docker daemon, the volumes or `.env` (which holds database passwords) controls the installation. Treat Docker group membership on the host as root.

## Authentication and authorization

Human UI passwords use Argon2 hashes. The `admin` bootstrap password hash is configured separately; set a strong password for setup, restrict the endpoint to trusted networks, and remove or disable that password after creating normal admin access when operationally possible. Login failures are limited in process by peer address. The limit is not shared across workers or restarts and does not replace network access control.

UI sessions are signed, client-side cookies with a 12-hour maximum age and `SameSite=Lax`. Configure a persistent, random `SECRET_KEY`; otherwise a new temporary key is generated on restart. Actor-backed sessions recheck active state and role against the database. Bootstrap sessions can outlive database setup and are not actor-backed until the user signs in again. All UI POST routes use a per-session CSRF token. The cookie does not currently set the `Secure` attribute because the same deployment supports HTTP LAN UI access; disable that access for sensitive deployments and protect the HTTPS endpoint against downgrade or HTTP reuse.

The API accepts bearer tokens, not UI cookies. Tokens are random and shown on creation or rotation; only SHA-256 hashes and short prefixes are stored in the database. Rotation replaces the old hash, and deactivation removes it. Treat the full token as a secret, use a separate token per actor, rotate on suspected exposure, and avoid passing tokens in shell history or logs. API login failures are also limited per peer in process. Anyone with an actor token can exercise that actor's API permissions.

`admin` has global management rights. `orchestrator` can plan and edit task workflows but is not an admin for user and setting management. `member` is a human role with project creation and owner-scoped management rights; an owner can manage their project. `worker` is the usual agent role. Authenticated humans can read and comment more broadly than the default owner-filtered UI view suggests. Treat all users with access as trusted with task contents; the owner filter is not a confidentiality boundary. Review role and project membership before granting tokens or Gitea collaborators.

## Gitea credentials and agents

Gitea service and per-actor tokens are Fernet-encrypted in the database using `<TBR_STATE_DIR>/master.key`. The master key is a separate file created with mode 0600; back it up separately and restrict access to the state directory, database backups, application environment, and logs. Encryption does not protect against a compromised application process or host. Rotate Gitea tokens at Gitea and update TaskBrigade when needed. Give the service token only the scopes described in the deployment documentation and give each actor the least access practical.

`GET /api/v1/agents/me/git-credentials` returns the caller's **plaintext** Gitea token to its bearer-token holder, only when the direct peer is loopback. This is intended for a local agent or a Tailscale HTTPS request through `tailscale serve`; the server cannot distinguish those two loopback sources. A stolen TaskBrigade API token used from either trusted path can retrieve that actor's Gitea token. The `tbr git-credential` helper requests it on demand and now releases it only when both the requested scheme and exact host including port match the configured Gitea URL. The helper does not store credentials; the runner clears inherited Git credential helpers in its clones. Keep each agent's `config.toml`, work directory, Git configuration, process environment, and logs private to that agent. Avoid embedding Gitea tokens in clone URLs or task text.

`POST /api/v1/join` (`tbr join`) exchanges a one-time join code for a fresh API token without a bearer token. It follows the same peer rule as the credential endpoint (loopback, `TRUSTED_PEER_NETWORKS`, i.e. `tailscale serve` or a local agent; `API_NETWORKS` peers get 403), counts failures towards the API rate limit, and accepts each code once until it expires (default 15 minutes). Only the SHA-256 of a code is stored; the audit log records creation and redemption without the code. A code is as sensitive as the token it yields until it is used: show it only to the person setting up the agent. The optional Gitea admin token (setting `gitea_admin_token`, encrypted like the service token) can create Gitea users; it is only used to create agent users, whose own tokens are created with their random, discarded passwords and carry `write:repository` and `read:user`. Leave the setting empty if that capability is not wanted.

Task descriptions, comments, attachments, repository files, and `brain.md` are untrusted input to an LLM agent. They can contain prompt injection that asks the agent to reveal secrets, change policy, run commands, or push unintended changes. The `local_only` / `cloud_ok` project flag limits assignment and membership for cloud-runtime actors, and switching an actor to cloud is checked against current local-only relationships. It is a workflow guard, not a sandbox or a content scanner. A local agent can still send data to a remote service if its runtime permits it; a cloud agent can receive copied text through a human or another tool. Run agents with narrowly scoped credentials and filesystem/network permissions, review generated changes and PRs, and keep secrets out of task and repository content. Rendered task Markdown disables raw HTML, but that does not make the instructions in the text trustworthy.

## Recommended operation

1. Install without Docker using the supplied systemd service; keep its dedicated `taskbrigade` user, restrictive state directory, `127.0.0.1` bind, one worker, and `--no-proxy-headers` setting. Put Tailscale HTTPS in front of it. With Docker Compose, keep the default `127.0.0.1` publish address and use the Tailscale sidecar; leave `API_NETWORKS` empty unless cleartext tokens on that network are an accepted risk. Patch the OS, Python dependencies, Tailscale, and Gitea regularly.
2. Set a strong `SECRET_KEY`, control `UI_ALLOWED_LOGINS`, and map allowed Tailscale identities to active human actors. Disable direct LAN HTTP UI access unless its confidentiality tradeoff is acceptable. Keep the API on HTTPS or loopback.
3. Protect and separately back up `master.key`, the database, `/etc/taskbrigade/taskbrigade.env`, and agent configuration. Test recovery and token rotation. Never publish a live database, key, token, or log sample.
4. Use distinct low-privilege agent identities and Gitea tokens. Review PRs and task-provided instructions as untrusted. Assign `local_only` projects only to local agents and audit any change to project privacy or actor runtime.

## Review findings and remaining work

Severity reflects the documented deployment, where the application host is trusted and port 8090 is not public.

| Severity | Finding | State |
| --- | --- | --- |
| Critical | No confirmed critical defect in the reviewed paths. Public exposure of the local listener or loss of `master.key` plus the database would invalidate the trust model. | Operational constraint |
| Medium | Any local process can spoof `Tailscale-User-Login` and reach the credential endpoint through loopback. An allowed but unmapped Tailscale login gets bootstrap access. | Documented trust boundary; stronger proxy authentication would need architectural work |
| Medium | In containers the direct peer is a Docker address; on Docker Desktop or behind the userland proxy every published-port client appears as the trusted gateway. | Documented: default publish on `127.0.0.1`, Tailscale sidecar keeps the loopback model, `API_NETWORKS` is a separate opt-in without header or credential trust; tests cover the new setting |
| Medium | Direct LAN UI access is HTTP, and the session cookie lacks `Secure`; local network observers can capture credentials or sessions. | Disable LAN UI or use an authenticated HTTPS proxy after reviewing peer/header trust |
| Medium | Agents can act on prompt injection in tasks or repositories; `local_only` is an assignment guard, not isolation. | Limit agent privileges and review outputs; sandbox design remains future work |
| Low | The Git credential helper previously released credentials for any requested host when the Gitea URL was missing, and accepted a host without its configured port. | Fixed: fail closed on missing or incomplete scheme/host match; regression tests added |
| Low | Unauthenticated `/healthz` exposed raw database and Gitea error text. | Fixed: status only; regression test added |

This review covers the identified authentication, token, network, and agent paths. It is not a penetration test or a guarantee against vulnerabilities in dependencies, deployment configuration, Git, Gitea, Tailscale, or agent runtimes.
